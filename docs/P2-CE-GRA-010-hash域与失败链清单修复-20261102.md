## 1. 修复内容

### 1.1 合法失败链与批次台账按相同 hash 域绑定

此前把 Client 回执中的 `receipt.request_sha256`（`digest([endpoint, HTTP body])`）与批次台账顶层的 `record.request_sha256`（`canonical_sha256(payload)`）直接比较。这两个计算对象不同，合法失败链因此会在整批 replay 被拒绝。

现明确分为：

- `payload_sha256`：与重建链的完整结构化 `request` 的 canonical SHA-256 比较；
- `transport_request_sha256`：与失败链中 Client 保存的 transport request hash 比较；
- `invocation_id` 和可用的 provider `response_sha256` 继续分别绑定。

没有修改历史台账的字段语义，也没有删去请求、父审核或跨调用绑定来使反例通过。HTTP、连接、超时等没有可解析响应的失败不伪造 provider response。

### 1.2 失败批次以台账要求失败链存在

此前目录缺链检查依赖 `generations`，但重建失败、尚无新图时该列表为空。现在 replay 按对应病例 `stage=reconstruction` 且 `provider_request_performed=true` 的台账计划/结算记录确定链数量；要求成对结算，并与目录中连续的 `reconstruction-*.json` 一一对应。

因此成功、模型 HOLD、响应校验失败、provider 无响应失败均已发生的重建调用均计入必需链清单，不再以 `generations=[]` 推断无需失败链。已有成功 generation 的链存在性、父审核 REVISE、完整请求和台账调用绑定继续保留。
