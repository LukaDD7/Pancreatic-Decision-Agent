## 1. 机制 A：一条理由被整表真值覆盖（代码缺陷）

### 1.1 位置

`scripts/cohort_construction/p2_auto_checkpoint_v04/engine.py:328-330`

```python
if 'CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT' in event.get('semantic_contract_validation', []) \
        or event.get('field_validation_errors'):
    reasons.append('CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT')
```

后半句对 `field_validation_errors` **整个列表取真值**，不是判断"列表中含该项"。
因此该事件只要存在任意一条字段错误，都会被追加 `CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT`
这条与真实错误无关的理由。

### 1.2 实测（SCALE-01..05，262 个事件）

| | 计数 |
|---|---:|
| 带 `CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT` 的事件 | 11 |
| 其中理由列表**只有这一条**（长度 1） | 11 |
| 其中真实 `semantic_contract_validation` 含该错误 | 4 |
| **不成立（真实错误是别的）** | **7** |

### 1.3 反例（稳定可复现的事件）

| 事件 | 真实 field_validation_errors | 被记的理由 |
|---|---|---|
| SCALE-01 `DE4efed346d79659aebd2b` | `SEMANTIC_PROOF_CURRENT_FACT_NOT_COVERED` | 仅 `CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT` |
| SCALE-02 `DE25c3b55adc41ea0fb81e` | `..._CONNECTION_OMITS_DECLARED_FACT` / `..._BASIS_OMITS_DECLARED_FACT` / `..._BASIS_OMITS_CONNECTION`（3 条，均非 action/fact） | 仅 `CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT` |
| SCALE-03 `DE3a0a193e5e...` | `..._FACT_NOT_UNIQUELY_VERIFIED` / `..._BASIS_NOT_UNIQUELY_VERIFIED` / `..._CURRENT_FACT_NOT_UNIQUELY_VERIFIED` | 仅 `CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT` |

### 1.4 后果

- **诊断失真**：这 7 个事件的失败原因在 `validation_reasons` 里完全看不到；
  真实原因是"证明结构未覆盖/未唯一核验"，不是"把当前动作当新事实"。
  任何按理由字段做的统计都会把 4 条和 7 条混为一类。
- **状态失真**：按 `engine.py:348-352`，`reasons` 非空即 `UNCERTAIN_CONTRACT_OR_SOURCE`。
  去掉这条误标后，上述 7 个事件**没有任何理由**，状态应为
  `CANDIDATE_NEW_MANAGEMENT_CHOICE`。即候选数被这一行少算了 7 个。
  （重算按 branch 复现，未执行写回；见 §1.6。）
- **修复目标失真**：这 7 个里有 4 个（全在 SCALE-02）被送进修复，
  却因父修复负载 1,841,232 / 2,118,467 / 2,639,595 字符超过 1,700,000 上限
  得到 `REPAIR_NOT_APPLIED / REVIEW_FEEDBACK_PAYLOAD_EXCEEDS_BUDGET`，
  一次都没有真正修复过。它们既没被正确归类，也没被修复。

### 1.5 归类

**代码缺陷。** 不是源资料问题、不是模型判错、不是研究设计问题。
修法是把条件改为对列表内容的成员判断（与前半句同义），
并保证每条被追加的理由能追溯到一条具体的 `field_errors` 记录。
修复必须带反例测试：一个只有 `SEMANTIC_PROOF_CURRENT_FACT_NOT_COVERED` 的事件
不得获得 `CURRENT_ACTION_USED_AS_NEW_PATIENT_FACT`。

### 1.6 未做的事

没有改代码、没有重算写回、没有在 0.8.0 运行中改动。上表"应为 CANDIDATE"
是按 `select_status` 分支离线复算得到的**推论**，不是已产出的结果。

## 2. 机制 B：被引用的前轮事件被两种方式拒绝发放（设计边界，代价需登记）

### 2.1 位置

- `engine.py:391-405` `earlier_ledger()`：同一处理单位内的事件默认不进入台账，
  除非双方都是 `explicit_documented_choice`。
- `engine.py:408-421` `eligible_prior_ids()`：只承认
  `time_order(chronology(previous), cutoff) == 'BEFORE'`。
- `context.py:44-47` `time_order()`：`relation_to_cutoff` 返回 `UNKNOWN_TIME`
  时统一变成 `'UNKNOWN'`。
- `prompts.py:85`（F 条）：明确要求 `previous_event_id` 只能取自该事件的
  `eligible_previous_event_ids`，并明确"共享 ledger 只提供身份重建上下文"。

### 2.2 实测（SCALE-01..05）

| | 计数 |
|---|---:|
| 引用了存在但未获许可的前轮 id 的事件 | 40 |
| 这类被拒 id 合计 | 40 |
| 其中**该 id 就写在模型读到的台账里** | 25 |
| 　└ 这 25 个的共同点：该事件的 `cutoff` 值为 `null`（`cutoff_basis = unknown_choice_time_no_prior_state_certification`） | 25/25 |
| 其中**台账里根本没有该 id**（同单位兄弟，被 `earlier_ledger` 跳过） | 15 |

### 2.3 两个子机制

**B1 — 截止时点未知时，任何前轮都不可能被许可（25 个 id）。**
`cutoff` 为 `null` 时，`time_order(...) == 'BEFORE'` 恒不成立，
`eligible_previous_event_ids` 恒为空集；但同一请求里 `earlier_event_ledger`
仍有 11 / 32 / 46 行事件可读，`context_for_discovery` 也把更早文书原文送进了发现阶段。
程序于是同时给出"这里有既往事件"和"一条都不许用"。
本批次 SCALE-01..05 中 `cutoff` 为 null 的事件共 42 个。

**B2 — 同篇兄弟既不显示、也不合法（15 个 id）。**
即使把兄弟放进台账，其中 7 个的 `time_order` 也是
`SAME_MINUTE_UNORDERED`（6）或 `SAME_TIME_UNORDERED`（1），判不为 BEFORE；
另外 4 个算出来是 `AFTER`——**这 4 个是模型引错了，程序抓对了**，
不能算作误拒。

### 2.4 反例

- B1：SCALE-02 `DEd505893e5f...`。请求里给了 11 行 `earlier_event_ledger`，
  `eligible_previous_event_ids = []`，`cutoff = null`；
  该事件引用 `DE1332f45e...`（确实更早，2021-05-22 16:51）。
- B2：SCALE-02 `DE12434074bc...`。它引用 `DE71544dae0e...`，
  两者都在单位 `DUdd8f2c30` 内，但 `DE71544dae0e` 不在台账中；
  且两者时钟同为 `2021-07-14 13:58:02`，即便可见也是 `SAME_TIME_UNORDERED`。
- 反向对照（程序正确）：SCALE-01 `DEaea3112a` 引用 `DE07b0527a`，
  `time_order` 算出 `AFTER`——模型把更晚的事件当成前轮，拒绝是对的。

### 2.5 后果：一处分歧产生多条理由，并切断图与 episode

一个被拒 id 会同时触发 2–5 条理由。例 SCALE-01 `DEe631e883`：其
`previous_event_id == same_process_previous_id`，一条分歧产生
`UNPROVIDED_OR_NONPRIOR_PREVIOUS_EVENT_ID` + `UNPROVIDED_OR_NONPRIOR_SAME_PROCESS_PREVIOUS_ID`
+ `UNPROVIDED_SAME_EVENT_ID` + `FINAL_GRAPH_TARGET_NOT_IN_PROVIDED_IDENTITY_EVENT_IDS`
+ `FINAL_GRAPH_TARGET_NOT_IN_PROVIDED_PRIOR_EVENT_IDS` 共 5 条。
本批次这类事件的理由条数分布：2 条 2 个、3 条 12 个、4 条 1 个、5 条 4 个。

图与 episode 的直接代价（`final_graph_audit.json` 的 blocked 依赖）：

| 例 | 被阻断依赖 | 其中目标就是被拒 id | 关系类型 |
|---|---:|---:|---|
| SCALE-01 | 10 | 8 | comparison 4 / process 4 |
| SCALE-02 | 29 | **29** | comparison 10 / process 18 / same_event 1 |
| SCALE-03 | 8 | 7 | comparison 2 / process 4 / same_event 1 |
| SCALE-04 | 18 | 12 | comparison 5 / process 5 / same_event 2 |

按现有许可连接的过程数，与"这些链接全部放行"时的过程数对比：

| 例 | 现有过程数 | 放行后 | 事件数 |
|---|---:|---:|---:|
| SCALE-01 | 22 | 18 | 36 |

**这不能说明放行就是对的。** 里面含 4 个模型确实引错的（`AFTER`），
以及若干同日无法定序的（拒绝是对的）。上表只说明代价的量级在哪个字段上，
不构成放宽规则的理由。

### 2.6 归类

**原则上是设计边界，有两处需要单独判断：**

- B2 中"同分钟/同秒不可定序"→ 保留。这是 AGENTS.md §4 与 §6 要求的时间证据边界。
- B1 中"cutoff 未知则一律不许"→ 需要研究判断，不能沿用现状默认：
  现在的效果是 42 个事件在任何情况下都不可能建立前轮关系，而模型仍然看到台账。
  要么明确这是"该时点不建立比较关系"的正式规则并写进合同，
  要么改为"cutoff 未知时提供显式的 `relation=UNKNOWN` 候选并要求模型标注不确定"。
  **两者都不是当前实现**，当前实现是"给材料、不给许可"。
- "一条分歧产生 5 条理由"→ 属于理由去重问题，与 B1/B2 独立，可单独登记。

## 3. 机制 C：证据通道在本数据类型上不可达（设计边界的实测确认）

r1 同四例为提案 64、存活 0、降级 64。**方向一致，0.8.0 只是让更多证据进入后
有 8 个恰好凑齐了引文包含关系，不是规则放宽。**

### 3.4 归类

**设计边界，但需要明确写成研究结论而非调试问题。**
在"没有独立发布时钟"的交付资料上，`report_time` 通道结构性不可用；
`evidence_informed` 型 Checkpoint 的产出量由这一条决定，
不能通过调上限、调并发或调温度改变。

## 4. 机制 D：两条路径的容忍度不对称（需确认是否有意）

`select_status` 对不同 `checkpoint` 提案的处理不同：

- `first_anchor` 带理由仍出 `CANDIDATE_FIRST_ANCHOR`（`engine.py:305-313`）。
  本批次 57 个 `CANDIDATE_FIRST_ANCHOR` 中 **36 个带至少一条理由**（63%）。
- `new_evidence` 只要有任一理由就落 `UNCERTAIN_CONTRACT_OR_SOURCE`
  （`engine.py:348-352`）。

因此"候选少"不能直接读成"模型判得差"：同一份理由，放在 A 路径仍算候选，
放在 B 路径就变成不确定。登记为待确认项，不改。
