## 3. 重复的来源（三类，量级已测）

1. **同一请求内的池内重复**：块级属性对整个请求恒定，或对同一来源恒定。
   每单位 220 个块中，`admissibility_role`、`time_provenance`、`availability_certified`、
   `publication_before_choice_certified`、`reading_before_choice_certified` 为池级常量，
   另有 9 个来源级常量字段重复 220 次。
2. **跨请求重复**：review 与 repair 共用同一池。SCALE-01 的单例是 13/13 单位
   review 与 repair 的 `evidence_source_pool` 逐字节完全相同；扩到 SCALE-01..05
   复核后为 **78/78 组配对全部逐字节相同**（`==` 成立，不是相似）。
   repair 输入合计 59,352,360 字符，其中池 38,297,363 字符，占 **64.5%**。
   SCALE-01 单例的块计数为 review+repair 发送 11,739 次、不同块 720 个；
   SCALE-01..05 合计为发送 **97,333 次**、不同块 **5,782 个**（来自 5,002 个来源），
   **重复发送占 94.1%**。各处理单位各自携带自己的池副本，共用同一批块。
3. **同一请求内的字段级重复**：repair 的 `validation_feedback` 内
   `allowed_revision_scope` 每请求重复 4 次（中位，最多 10 次），
   占 `validation_feedback` 字节的 **58.4%**；其子项 `source_ids`、`evidence_object_ids`
   逐次完整重发。台账 `action_quotes` 内 `quote` 与 `citation.quote` 重复（占台账 4.2%），
   另有 `source_sha256` 字符串占台账 9.5%。

## 4.1 术语澄清：`parent_repair_payload_characters` 不是"上一轮"

`review_feedback_audits.json` 里的 `parent_repair_payload_characters`
**不是**历史对话轮次，也不是"上一轮回复 + 本轮"的累加。它是：

> 在**同一次** review 请求的基础上，把 `events` 收窄到需要修复的那几个事件、
> 加上 `validation_feedback` / `original_proposals` / `repair_contract` 之后，
> 准备发给提供方的**第一个修复候选负载**的字符数（`review_feedback.py:125-128`
> 的 `payload = prepare_payload(...)` 之后的 `size`）。
> 命名里的 "parent" 指它所源自的**父 review 请求**，不是"上一轮对话"。

逐字段实测（SCALE-01 单位 `DUe4fa94e0f63f2d2f9a6d`，review → repair 同一输入）：

| 字段 | 变化（字符） |
|---|---:|
| `evidence_source_pool` | **0（逐字节完全相同）** |
| `earlier_event_ledger` | **0（完全相同）** |
| `current_full_document` / `instruction` 以外的固定字段 | 0 |
| `validation_feedback` | +132,615 |
| `original_proposals` | +3,830 |
| `instruction` | +531 |
| `repair_contract` | +200 |
| `events`（收窄到目标事件） | −23,946 |
| 合计 | 901,875 → 1,015,187 |

结论：**修复请求没有"再次读取病历"，它把 review 已经发过的池原样再发一遍，
只增加了反馈文本。** 这正是 §3.2 跨请求重复的来源。

## 4.2 负载为什么这么大：不是对话累积，是"单事件 × 每单位池 × 每事件一次"

**先否定一个直觉**：本流水线**没有**多轮对话上下文累加。
抽样检查 `live-window088-cache` 中的请求，`messages` 一律是 `[system, user]` **两条**，
没有任何历史轮次被回传。所以不存在"第 N 轮把前 N−1 轮的对话全带上"这种线性相加。
每个请求都是独立一次交换，**同一事件的费用按它经过的请求次数相加，而不是按对话轮次累加**。

实际的三层放大：

1. **单位内**——同一处理单位的所有事件共用**一个**池（`engine.py:646-661`）。
   单位有 2 个事件，池不是各发一份，而是发一份。所以"事件数"不线性放大池；
   但**池本身**按该单位全部相关来源区间构建。
2. **单位间**——每个单位各自携带自己的池副本。SCALE-01..05 的 review+repair
   合计发送 97,333 个块，而这些块只来自 5,782 个不同的块（§3.2）：**同一段原文
   在不同单位的请求里被重复发送，重复占 94.1%**。这是最大的一层。
3. **review → repair**——78 组 review/repair 配对中，**78/78 的池逐字节完全相同**
   （不是"相似"，是 `==` 成立）。repair 输入合计 59,352,360 字符，
   其中池 38,297,363 字符，占 **64.5%**，全部是上一份 review 刚发过的内容。

**池内部还有一层，量级最大**：本批次 184 个含池的 review 请求，
池 JSON 合计 86,622,584 字符，其中块原文（`text`）仅 14,279,487 字符——
**元数据脚手架占 83.5%**，平均每块 1,085 字符的键名、引号、时间与状态字段，
而块原文中位 146 字符。单请求脚手架占比最低 52%、中位 83%、最高 98%。

## 5. 实施前置条件（登记，不是本轮的改动）

- 每项减量都必须证明**解码后与原始池逐字节相同**（`payload_codec.decode_pool`
  已有该不变量与 `POOL_SOURCE_FIELD_VARIES` / `POOL_CONSTANT_FIELD_VARIES` 抛错路径）。
- TOK-02/TOK-03 是**删除字段**而非改表示，不能靠解码恢复，必须先在提示词与
  下游校验中确认这些字段当前没有被模型实质使用；删除后要有反例测试证明
  模型判断不变，否则只能作为等价别名（如"未提供即等于 clock"）写进提示词。
- TOK-05 会改变块标识的书写方式，必须同步更新模型输出契约中对 `block_id` 的要求
  与程序端匹配逻辑，不能只改发送端。
- TOK-07 改变请求数量与语义分层，属于接口变更，需单独方案，不能与减量混做。
- 上限改为 token 口径（而不是字符数）仍需独立登记：0.8.0 仍是字符口径。
