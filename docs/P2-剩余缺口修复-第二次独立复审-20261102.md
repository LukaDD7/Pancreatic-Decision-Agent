## 1. [P1] CE-GRA-010/HASH_DOMAIN：两种请求 hash 混用，合法失败链导致最终批次 replay 报错

代码位置：

- `p2_auto_checkpoint_v04/client.py:119`：Client 的 `receipt.request_sha256` 为 `digest([endpoint, HTTP body])`，其中 body 包含模型参数、system 提示、Schema 和 payload。
- `p2_checkpoint_real_validation/budget.py`：台账顶层 `record.request_sha256` 为 `canonical_sha256(payload)`；Client 的传输请求 hash 另存在 `record.receipt.request_sha256`。
- `p2_checkpoint_reconstruction_audit/reconstruction.py:295–298`：异常分支把 Client 的传输请求 hash 写入 `failure.request_sha256`。
- `p2_checkpoint_real_validation/batch.py:342`：预期绑定返回的是台账顶层 payload hash。
- `reconstruction.py:380–382`：将上面两个不同计算对象的 hash 直接比较。

因此，并没有错放请求或修改来源的合法失败链，也会抛出 `GRAPH_RECONSTRUCTION_LEDGER_REQUEST_BINDING_MISMATCH`。

**独立反例已复现：**

1. 生产 `Client` + 生产 `BatchModelBudget` + mock HTTP，返回 JSON 可解析但 Schema 不合格的占位图：响应和调用 ID 均已保留，独立链 replay 成功；加上真实父请求和台账绑定后却失败。
2. 相同路径模拟连接失败：调用 ID 已保留，独立链 replay 成功；父请求和台账绑定同样失败。
3. 完整 `execute_batch`，使用生产 Client，仅 mock HTTP：首次图审核成功要求重建，重建十次 Schema 失败。全部 11 次 HTTP attempts 均由 mock 提供；进度已保存，但批次末尾 replay 抛出上述错误，`batch-execution-receipt.json` 未创建。

示例中传输请求 hash 为 `2257afc5…53b1522a`，payload hash 为 `05a44a88…3f49718`，两者按定义就不应相等。

**为何现有测试未发现：** 批次 provider 失败 mock 的 receipt 省略了真实 Client 必有的 `request_sha256`，因而绕过这条比较；生产 Client 的异常测试没有核验一个未被修改的链在真实台账绑定下能够通过。它只对被修改的请求做负对照，不能验证合法链正对照。

**必需修复与回归：** 明确区分 payload hash 与传输请求 hash，将每个 hash 与相同计算对象比较；保留旧结果的字段语义，不通过删去绑定检查修复。新增“生产 Client + mock HTTP + 真实批次台账”的合法失败正对照，覆盖 Schema 失败、连接/超时失败，并保留错误请求和跨调用负对照。
