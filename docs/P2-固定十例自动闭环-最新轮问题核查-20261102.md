## 1. 已定位的主要原因

### CE-GRA-008：实际重建请求错误地使用图审核提示

**已由六份实际 provider 请求证实。** 六份重建缓存请求的 system 消息均与当前 `GRAPH_AUDIT_INSTRUCTIONS` 完全相同，均不等于专用重建 `INSTRUCTIONS`。

- `p2_checkpoint_real_validation/batch.py:213` 将 `graph` 适配器绑定至 `graph_audit_client(client)`。
- `p2_checkpoint_ready_pipeline/automatic_revision.py:31` 再取这个 `graph` 适配器执行重建。局部预算虽标成 `reconstruction`，实际 system 消息及批次台账仍沿用图审核路径。
- `p2_checkpoint_reconstruction_audit/reconstruction.py:47` 定义的 `graph_reconstruction_client` 未接入这条真实执行路径。
- 图审核提示明确要求“审计层不得直接修改事件图”，还要求审核证据位于 `audit_scope.complete_originals_supplied`；重建请求却将原文放在顶层 `complete_originals_supplied`。
- SCALE-10 的响应理由明确称自己是无权修改事件图的审核者；SCALE-06 明确称未看到 `audit_scope`，且接口没有 HOLD 输出。这些理由与实际错误提示相吻合。

这能确认提示接线错误；尚不能声称只修这一个问题即可成功重建全部病例。

### CE-GRA-009：重建 Schema 允许占位对象，业务校验才拒绝

**已读取并离线复现六份实际响应。**

| 病例 | 缓存响应的 `graph` |
| --- | --- |
| SCALE-02、03、04、07、10 | `{"、":["、"]}` |
| SCALE-06 | `{"、":null}` |

六份响应均缺少 `events / relations / episodes / graph_version`；不是仅多了字段、版本号放在外层或多包一层对象。部分 `rationale` 声称已经重建，但没有对应图结构，不能作为完成证据。

`GRAPH_RECONSTRUCTION_SCHEMA.properties.graph` 实际只有 `{"type":"object"}`，因此上述占位对象通过 transport Schema；随后 `validate_graph_reconstruction` 要求四个字段恰好齐备，全部拒绝。六份缓存请求的用户消息本身都可被 JSON 解析；SCALE-07 理由中的“输入 JSON 语法无效”不能认定为程序输入错误。

接口同时缺少明确的“不能重建/HOLD”响应分支。须对齐 Schema、重建提示和业务校验，定义新图事件/关系/候选 Episode 的字段约束，以及程序负责保留的来源清单和处理单位。不能通过接受占位图、删去引文校验或把拒绝理由改名为成功来修复。

### CE-REAL-012：Episode 原文范围与历史模型证据范围不一致

**SCALE-01 已核实到冻结交付原文。** `inputs.load_episode_case` 只交付所选候选 Episode 事件所属处理单位的原文，本例共 3 份；但保留了历史事件对象中的 `actual_model_evidence`。材料装配按 `event.source_ids ∪ actual_model_evidence[].source_id` 要求完整来源。

| 候选 Checkpoint 事件 | 材料请求来源数 | 本次 Episode 原文中缺少 | 缺少部分在冻结交付包中找到 |
| --- | ---: | ---: | ---: |
| `DE5af4447a2aeb5613ff90` | 245 | 243 | 243 |
| `DE70a3e2a3c2a650178fbc` | 257 | 254 | 254 |

两事件自身 `source_ids` 均只有 1 份，缺口来自历史 `actual_model_evidence`，不是事件自己声明了两百多份文书。两组缺少来源均完整存在于该病例冻结交付资料中；不能表述为患者未做检查、医院没有报告或原文读取失败。

图审核的 `source_coverage_complete` 只比较声明处理单位与本次提供原文，因此它可以为真，而材料装配仍因历史证据依赖未交付而 HOLD。修复应显式组织本次审核原文与历史证据来源依赖，保留冻结事件及来源历史；不能直接取来源交集、悄悄删除历史证据，或未经设计就将全患者资料放入医生盲评文件。

### CE-GRA-010：失败重建链没有保存响应，批次 replay 没有复验该失败链

**代码与产物共同证实。** `run_graph_reconstruction` 的异常分支未保存已返回的 `response` 和 `provider_receipt`。六份响应仍可从私有 `model-cache` 找到，并非证据完全丢失。

`batch.replay_batch` 在无成功新图时仍复验父 `run.json`，读取自动修订摘要，但不读取并业务复验独立的 `reconstruction-0001.json`。因此既有“十例 replay 通过”是十条父运行链的校验结果，不能扩展成“七条失败重建链均已完整业务重放”，更不能证明闭环成功。

| SCALE-09 图重建 | JSONDecodeError ×8；ValidationError ×1；ReadTimeout ×1 |

全批次为 **17 个逻辑请求、62 个 HTTP attempts、0 个本地缓存命中**。14 次 attempts 返回了可通过 transport Schema 的结果；48 次失败包括 Schema 不合格 19、JSON 解码失败 14、读取超时 12、连接错误 2、TLS 错误 1。

所以“本轮没有响应校验失败”必须限于：最终进入图审核业务校验的响应没有重现旧 `SOURCE_UNKNOWN / QUOTE_NOT_UNIQUE`。它不涵盖 transport 内部重试的 19 次 Schema 失败，也不涵盖六次重建业务校验失败。仅凭现有异常类型不能判断每次 JSON 解码失败发生在 HTTP 外层还是模型正文，亦不能推断供应商具体故障原因。
