## 1. [P1] CE-REAL-012：补齐来源没有传入首次正式材料装配

定位：`scripts/cohort_construction/p2_checkpoint_real_validation/batch.py:254–262`；`p2_checkpoint_ready_pipeline/orchestration.py` 继续用同一个 `sources` 参数执行图审核和材料装配。

`load_episode_case` 和预检现在能够返回材料所需来源依赖闭包，但 `execute_batch` 首次调用 `run_episode_pipeline` 时只传 `sources=current_sources`，并未把补齐的材料来源交给材料阶段。图审核 PASS 后仍以这个窄来源集合调用 `prepare_candidate_materials`。

**真实冻结资料的只读核验：** SCALE-01 的预检来源为当前处理单位 3 份、材料来源 257 份，预检材料失败数为 0；按正式批次首次运行的实际参数执行无落盘 pipeline、由 mock 返回图审核 PASS 后，仍得到 HOLD：

- `DE5af4447a2aeb5613ff90`：`ASSEMBLY_SELECTED_SOURCE_MISSING`，缺 243 份。
- `DE70a3e2a3c2a650178fbc`：同一错误，缺 254 份。

虚构的完整 `execute_batch` 反例也复现：预检持有 4 份来源、当前单位持有 3 份，历史来源已在交付包中，首次 PASS 后仍报缺源。现有 CE-REAL-012 测试只测试来源闭包函数；批次 adapter 测试则将两份来源文件写为相同集合，没有覆盖实际范围不同的情况。

**必需修复/回归：** 将图审核原文集合与材料来源集合分别贯穿正式执行、输入契约和 replay；新增“首次图审核 PASS + 历史依赖已恢复”的批次级测试，确认材料阶段收到恢复来源，并保留时间可见性和医生许可核验。

## 2. [P1] CE-REAL-012：成功重建后扩大图审核原文范围，导致 PASS 条件无法满足

定位：`batch.py:278–280`；`p2_checkpoint_ready_pipeline/automatic_revision.py` 将该 `sources` 传入重建后的 `run_episode_pipeline`。

正式批次首次审核使用 `current_sources`，自动修订却收到 `sources`（当前原文与历史材料依赖合并集合）。重建本身从父审核请求取得当前原文；重建成功后的全新图审核却使用这个合并集合，处理单位仍是原来的当前单位。

**已在完整虚构批次中复现：** 首次图审核收到 3 份原文，`source_coverage_complete=true`；专用重建接口成功返回并保存新图后，全新图审核收到 4 份原文，历史来源 `DOC-BUDGET` 落入 `uncovered_supplied_source_ids`，`source_coverage_complete=false`。此时审核模型即使输出 PASS，现有业务校验也必然拒绝，终态为 `AUTO_GRAPH_AUDIT_HOLD`。

这还违背实施回执中“图审核和独立重建继续只使用当前处理单位原文”的说明。不能以放宽覆盖检查解决；应与第 1 项一起显式分离两类来源范围，并在每代新图和 replay 中保持声明一致。

## 3. [P2] CE-GRA-010：真实 Client 的 Schema 失败仍不保存响应，provider 调用身份也遗漏

定位：`scripts/cohort_construction/p2_auto_checkpoint_v04/client.py` 的 `Client.ask`；`p2_checkpoint_reconstruction_audit/reconstruction.py:264–273`。

新增保存逻辑只覆盖 `ask` 已经返回响应后的校验失败。实际 `Client.ask` 会先校验 Schema；现在占位图被 v0.2.0 Schema 拒绝，异常在 Client 内部重试，最终抛出 `ModelRequestFailed`，响应正文仍没有进入缓存或失败重建链。

**已用生产 Client 离线复现：** 只替换 HTTP 方法，返回虚构、JSON 可解析的占位图响应，尝试次数设为 1。结果为 `PROVIDER_REQUEST / ModelRequestFailed`，独立链无 `response`、无 `provider_receipt`；Client 自己的失败回执有 `invocation_id`，独立链却没有保存它，因为异常分支没有从 `exc.receipt` 取回回执。

现有“失败响应保存”测试用 mock 直接返回不合格对象，绕过真实 Client 的 Schema 校验；因此它通过不能证明这条真实路径已修复。

**必需修复/回归：** 对传输解析/Schema 失败提供私有、可追溯的响应或脱敏结构诊断留存；从请求专属异常回执恢复调用身份。使用真实 Client + mock HTTP 验证这条路径，而非仅 mock `ask` 返回值。无响应时仍不得伪造响应正文。

## 4. [P2] CE-GRA-010：provider 失败链跳过请求校验，批次未绑定失败链与父运行

定位：`reconstruction.py:313–327` 的提前返回；`batch.py:334–348`。

- provider 失败分支在 `_validate_request` 之前返回 `replay_verified=true`。离线修改失败链 `request.input_graph.graph_version`，不更新图 hash 或原请求 binding，只重算链自 hash，仍被接受。
- 批次 replay 对成功链核对 generation 绑定，对 HOLD 链只检查状态。没有核对失败链的输入图、重建请求、父审核 REVISE、病例及台账调用身份。

**已复现：** 将来自另一输入图的完整 provider 失败链放进一个虚构批次的修订目录，该批次甚至没有提出重建，`replay_batch` 仍返回 `replay_verified=true`。操作只作用于本次新建的虚构输出，未改真实批次。

**必需修复/回归：** 所有分支先核验请求；成功、模型 HOLD、响应失败、provider 失败均绑定对应父审核/重建请求与台账 invocation。增加请求修改、跨病例/跨图链错放、缺少预期链的负对照，保留合法失败可重放的正对照。
