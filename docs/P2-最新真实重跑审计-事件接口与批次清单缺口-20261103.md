## 2. CE-GRA-011：重建事件 Schema 与材料装配事件接口不一致

### 真实产物已证实

十例完整批次中，下列新候选图已完成重建并通过新一轮独立图审核，但材料装配均因 `EVENT_SOURCE_IDS_REQUIRED` 停止：

| 病例 | 新图事件数 | 材料装配中该错误数 |
| --- | ---: | ---: |
| SCALE-03 | 1 | 1 |
| SCALE-04 | 6 | 6 |
| SCALE-06 | 2 | 2 |
| SCALE-10 | 6 | 6 |

四份实际重建响应的事件均只包含 `event_id`、`source_id`、`checkpoint_status`、`action_citations` 四个字段。重建程序随后补充证据上下文，但未补充或强制核验材料接口需要的 `source_ids`。15 条装配错误属于这四个病例的新图事件接口问题，不是 15 名患者，也不是患者源资料质量差。

### 代码依据与反例

- `p2_checkpoint_reconstruction_audit/reconstruction.py:46` 的事件 Schema 仅要求上述四个字段。
- 同文件 `validate_graph_reconstruction` 校验动作引文、重新生成证据上下文并冻结新图，但不核验完整下游事件接口。
- `p2_checkpoint_materials/prepare.py:86` 明确要求 `event.source_ids` 为数组，否则拒绝。
- `p2_checkpoint_reconstruction_audit/tests/test_graph_reconstruction.py` 的 `proposed()` 从完整既有事件复制响应，因此既有成功测试天然携带下游字段，未覆盖“只返回 Schema 必需字段”的响应。

独立虚构反例通过生产 Schema、重建校验和材料装配函数依次执行：

| 对照 | Schema 与重建校验 | 材料装配 |
| --- | --- | --- |
| 完整事件对象 | 通过 | 2 个任务，0 失败 |
| 仅移除 `source_ids` | 通过 | 0 个任务，2 个 `EVENT_SOURCE_IDS_REQUIRED` |
| 事件只保留 Schema 必需的四个字段 | 通过 | 0 个任务，2 个同类错误 |

因此，“新图已生成且重新图审核 PASS”不能证明新图能被材料接口消费。此前工程修复解决了占位图问题，但尚未保证重建事件的下游兼容性。

### 修复及必需回归清单（待实施）

1. 明确重建事件、来源清单、时间与原文引文的完整交接契约，并对齐 Schema、提示和确定性校验。缺少临床判断依据时须保留待核，不得由程序补造时间或临床事实。
2. `source_id` 与 `source_ids` 应有明确一致性约束；多来源事件须保留全部声明来源及证据来源，不能无条件把所有事件压成单来源。
3. 不能只增加 `source_ids=[source_id]` 就宣布完成：实际四字段响应还缺少其他既有事件信息。应分别规定必须保留、程序可重建及明确未解决的字段，并验证其时间和遮蔽含义。
4. 新增正式回归，覆盖完整事件正对照、缺字段反例、四字段最小响应、多来源与主来源不一致、未知来源，以及真实执行路径“重建→新图审核→材料装配”。测试必须迁入正式问题回归清单并执行相应完整守卫。

## 3. CE-REAL-013：首次或恢复批次 replay 未建立独立病例清单

### 虚构反例已确认，适用条件须保留

`p2_checkpoint_real_validation/batch.py:354` 仅遍历 `progress['cases']`。重建调用清单也在这个循环内部按当前病例查询；循环结束后只检查台账记录是否有 `expected_gain`，没有检查台账是否还包含未被进度表列出的病例。

在使用生产 Client、生产 `execute_batch` 和 mock HTTP 生成的合法虚构失败批次中：

- 完整批次 replay 通过，保留两次逻辑调用及失败重建链。
- **既有批次 replay 回执保留时**，改写进度汇总会被 `REAL_BATCH_RECEIPT_CHANGED_REQUIRES_NEW_OUTPUT` 拒绝。这项保护有效。
- **没有既有批次 replay 回执时**，将进度表病例清单置空，台账及原始运行链保持不变，replay 返回 `replay_verified=true`、`fixed_case_count=0`，同时仍报告 2 次逻辑调用。
- 同一条件下，将进度表改为仅列另一个子集外未尝试项，replay 仍返回通过；实际被调用病例的失败重建链完全未进入核验循环。
- 恢复原始进度表和既有回执后，合法完整批次再次通过。

上述变更仅发生在本次新建虚构临时目录。**没有修改真实进度表、删除真实链或移走真实回执。** 此反例说明首次生成或恢复回执时存在病例清单核验缺口；不能声称已经证明最新完整批次丢失了某个被调用病例的链。

### 真实材料中观察到的边界

- 中断批次的进度表列 2 例，台账另含 SCALE-05；该病例保存的 `run.json` 无法被 JSON 解析。此批次没有最终执行回执，不能报告其完整 replay 已通过；中断写入问题不能归为患者病历不可读取。
- 后续批次的 5 个授权病例均在进度表中。`fixed_case_count=8` 来自 5 个授权病例加 3 个子集外未尝试项，SCALE-09、10 未列入该回执。两者均不在这次五例授权子集中，因此这不是漏跑授权病例的证据，但该字段不能解释为固定十例分母或五例成功数。

### 修复及必需回归清单（待实施）

1. 从冻结批次清单、授权子集、台账调用与实际产物建立独立病例清单，再核验进度表覆盖、重复项和各病例终止/中断状态。
2. 台账中有调用但无进度结果或未结算时，应明确拒绝完整完成声明或记录不完整状态，不能跳过该病例后汇总 PASS。
3. 分开报告固定来源病例数、授权病例数、实际尝试数、已完成核验数及未尝试数；恢复运行保留父运行绑定和累计预算口径。
4. 新增正式回归：无既存回执且进度清单为空、部分丢行、有台账无进度、仅剩子集外项、重复病例、合法授权子集、合法中断恢复，以及既有回执不变保护。
