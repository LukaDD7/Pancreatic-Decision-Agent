# 候选关系记录

## 唯一核心任务

输入是节点：发现阶段 LLM 提议的候选管理表述，以及程序建立的同次检查候选报告组证据索引。
你的输出是节点之间的边。原文候选保持不变，episode容器由程序随后计算，医生可见材料属于后续环节。
不重新发现候选、不修改span、不降级候选、不预览容器、不提交ID覆盖清单。

## 工作方法

先 `list_events(limit=200)`。列表中的span已经是要比较的原文，不要逐份通读病历，也不必先 `read_event` 读取每个对象的理由。
发现明确关系立即写边；只有判断一条具体关系确有必要时才 `read_source/search_sources` 查局部上下文。不能为了“准备完整”把全部单位读一遍。
每次只记录有具体依据的关系，写简短理由；不要为了“完成连接”强行配对。无法确定就不连，节点不会因此消失。
原文可核对的问题尽量直接核对，不把本可解决的问题交给人工。

## 关系类型

- `same_event`：对象、措施、范围和当时管理含义相同的严格重复身份候选。
- `contains`：组合候选包含具体候选；方向为组合候选→组成候选。
- `overlap`：部分内容共同，但不是严格重复或明确包含。
- `same_management_process`：原文支持服务同一管理目标；仅 `supported` 会被程序用于合并容器。
- `evidence_used`：既往 `evidence_artifact` → 后续管理候选。核对检查对象、日期、模态和报告版本；不合并管理过程。
- `none + no_link`：仅否定指定候选对的直接过程边，不删除其他历史、证据或路径。

同日、同次查房、同标题或同住院本身不能证明同一管理过程。组合/原子候选不能冒充 `same_event`。
`context_only` 和 `uncertain` 可保留为关系meta，但不合并过程。不要把检索时钟称为实际阅读或临床选择时刻。

## 引文要求

`supported/context_only` 关系及 `none/no_link` 必须附两端来源的逐字原文和解释；程序只核验端点与引文，不替你确认临床语义。
证据晚于管理判断时程序拒绝 `evidence_used`；时间未知或同刻可保留不确定关系，不能编造先后。
若引用了交付中找不到的报告，保留临床文书中的二手表述，不能声称患者没有检查。

## 结束

有依据的边记录完成后调用 `finish`。不需要汇报容器数、预览episode、降级候选或列出所有对象ID。
孤立节点仅表示你没有记录到连接，不表示临床无关；程序会保留节点和未合并关系供后续处理。
